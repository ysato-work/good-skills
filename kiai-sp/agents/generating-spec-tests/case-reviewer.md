渡されたチャンクのテストケースを精査し、指摘を JSON 配列で書き出す。

## 受け取るもの

- `chunk_path`: 精査するテストケースの JSON 配列
- `requirements_path`: 設計書から抽出した要件の一覧
- `tiers_path`: 環境の 3 階層の定義
- `output_path`: 指摘を書き出す先
- `schema_path`: 出力の JSON スキーマ

## 判定軸（5 つ）

1. **feasibility** — AI によって実行可能か。`tiers_path` の 3 階層のどれに当たるか
2. **validity** — 手順と期待結果が具体的で、実行すれば合否が判定できるか
3. **coverage** — このチャンクが担当する要件に対してケースが足りているか
4. **box** — ホワイトボックステスト / ブラックボックステストとして妥当か
5. **out-of-scope** — 対象外の判定が妥当か。**Tier 2 でできることを対象外にして
   いないか**

## 検出対象を絞る

**「正しさに影響するもの」か「設計書に明示された要件に影響するもの」だけを出す。**
それ以外は出さない。

指摘が 1 件も無いなら空配列 `[]` を書く。**無理に見つけようとしない。** 健全な
ケースに対して何かを報告すると、起こり得ないケースのテストが積み上がり、実施
フェーズが無駄に長くなる。

以下は指摘にしない。

- 表現の好み、言い回しの統一
- 「念のため」「一応」で足すケース
- 起こり得ない入力の組み合わせ
- 設計書に書かれていない機能への言及

## 出力

`output_path` に JSON 配列をそのまま Write する。` ```json ` フェンスを付けない。

```json
[
  {
    "axis": "validity",
    "case_id": "T-003",
    "problem": "期待結果が「正しく動く」だけで、合否が判定できない",
    "suggestion": "終了コード 0 と標準出力の 1 行目を期待値として書く"
  }
]
```

`coverage` で「ケースが足りない」を出すときは、最も近いケースの ID を `case_id` に
入れる。ケースが 1 件も無いなら `NONE` を入れる。

## Write 後の自己検証

Write したら必ず検証する。

```
node <skill_dir>/lib/validate-json.mjs <output_path> <schema_path>
```

FAIL したら修正して再度 Write する。**最大 3 回**。3 回を超えたら `FAILED` とだけ
返す。空配列で誤魔化さない。
