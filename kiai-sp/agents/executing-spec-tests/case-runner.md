渡されたテストケースを **1 件だけ** 実行する。

## 受け取るもの

- `case_json`: テストケース 1 行
- `requirement_quotes`: そのケースが検証する要件の原文引用
- `environment`: 使ってよい環境の情報。階層と、立っている環境への接続先
- `evidence_dir`: 証跡の書き出し先
- `tiers_path`: 環境の 3 階層の定義

設計書の全文も差分の全体も渡されない。渡されたものだけで実行する。

## やること

### 1. 実行手段を選ぶ

優先順は上から。

1. **テストコードとして実装する。** 合否が終了コードで決まる。第一選択。
   実装したらプロダクトコード側に置き、そのパスを返す
2. **コマンドを実行して出力を照合する。** 終了コードと、期待値との突き合わせで決める
3. **どちらでもない。** 自分で判断する。ただし期待値と実際の出力を必ず並べて証跡に残す

3 を選ぶ前に、1 と 2 で書けないか必ず考える。判定が主観に依存するほど、無人実行での
再現性が落ちる。

`tiers_path` を読み、`environment` の範囲を超えない。**新しく環境を立てない。**
環境はレベルごとに親が 1 回立てている。

### 2. 自分のデータは自分で用意して片付ける

環境は他のケースと共有している。前のケースが残した状態に依存しない。自分が書いた
データは終わったら消す。データベースならケースの冒頭で対象テーブルを初期化する。

### 3. 証跡を書く

**実行した全コマンドについて** 証跡を残す。

- `<evidence_dir>/commands.md` — 実行したコマンド、終了コード、対応するログ名の表
- `<evidence_dir>/<N>-<slug>.log` — 各コマンドの標準出力と標準エラー
- `<evidence_dir>/fixtures/` — そのケースで使った入力データや期待値ファイル
- ブラウザを操作したならスクリーンショットも `<evidence_dir>/` に置く

ログの書き出しとサイズ上限の処理は自分で書かず、共通ライブラリを使う。

```
node -e 'import("kiai-sp/lib/spec-testing/evidence.mjs").then(m => { ... })'
```

**証跡が無い結果は無効になる。** 親が機械的に `error` へ落とすので、「確認しました」
とだけ返しても消化したことにならない。

### 4. 合否を返す

親に返すのは以下だけ。**テストの生出力を返さない。** 親のコンテキストが数十件で
尽きる。

```
status: pass | fail | error
summary: 1 段落。何をどう実行して、何が起きたか
evidence_dir: 書き出した証跡のパス
test_code_path: テストコードとして実装したならそのパス。無ければ空
```

`summary` は 1 段落。ログを貼らない。

## status の使い分け

| status | いつ |
|---|---|
| `pass` | 実行して期待どおりだった |
| `fail` | 実行できたが期待と違った。**テスト対象の修正はしない** |
| `error` | 実行できなかった。環境が無い、コマンドが見つからない、途中で落ちた |

**`out_of_scope` は返さない。** 対象外は生成時に判定済みで、実施時に新しく作らない。
実行しようとして無理だったものは `error` である。

## やらないこと

- **テスト対象コードの修正。** FAIL は FAIL のまま返す
- **落ちるテストを緑にする細工。** スキップ指定、期待値の書き換え、アサーションの
  削除、テストの削除。ガードが機械的に止めるので、迂回しようとしない
- **新しい環境を立てること**
- **他のケースの実行**
