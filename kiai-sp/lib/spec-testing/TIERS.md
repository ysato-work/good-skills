# 環境の 3 階層とテストコードの規律

S3 のレビュー合議と S4 の実施がこの文書に従って階層を判定する。

設計の根拠は `docs/superpowers/specs/2026-08-31-テスト環境の境界と汚染防止-design.md`。

実行場所は固定しない。開発者のマシン、ステージング、クラウド上のコンテナ、どこでも
同じ判定で動く。

## Tier 1: 既にあるものを使う

リポジトリに既に存在するテスト手段。パッケージマネージャのスクリプト、既存の
compose ファイル、CI 設定に書かれた手順。**第一選択。** そのまま使う。

外部のスキルや別の手段で用意された環境も Tier 1 として使う。受け取り方は 2 通りだけ。

1. リポジトリ内の記述（スクリプト、compose ファイル、CI 設定）。第一選択
2. スキル起動時の引数（接続先、アクセストークンなど、リポジトリに書けないもの）

**環境変数からの暗黙の取得はしない。** どの環境に対してテストしたのかが証跡から
辿れなくなる。引数で受け取った接続先は `report.md` に記録する。認証情報そのものは
記録しない。

## Tier 2: このスキルが立ててよい環境

以下を **すべて** 満たすものだけ、自分で立ててよい。

1. **立ち上げ手順が判明している。** リポジトリの記述、公式イメージの標準的な起動方法
   など、根拠のある手順が実在する
2. リポジトリ内で完結する。外部サービスへの認証情報を必要としない
3. 通信先が localhost だけで済む
4. 認証情報はテスト専用の固定値でよい
5. 開発者の既存の状態に触らない。既存のコンテナ、既存のボリューム、既存のデータベース、
   既に使用中のポートを一切使わない
6. テスト終了時に確実に破棄できる

条件 1 を先頭に置いているのは、これが実現可能性の条件で、残りが安全性の条件だから。
安全に立てられるかより前に、そもそも立て方が分かるかを見る。

典型例は、データベースを使うクエリの検証。テスト用の Postgres をパスワード固定で
立て、アプリケーションをそこに接続してテストし、終わったら破棄する。**この程度の
ものは対象外に落とさず、実行する。**

### 名前で自分の資源と開発者の資源を分ける

- コンテナ・ボリューム・ネットワークの名前は **`spec-testing-`** で始める
- `docker compose` は **`-p spec-testing-<なにか>`** を必ず付ける
- push してよいブランチは **`spec-testing/`** で始まるものだけ
- **立てたデータベースの名前も `spec-testing-` で始める。** ガードは localhost への
  書き込みを既定で止めるが、コマンドの中に `spec-testing-` が出ている接続だけは
  自分が立てた使い捨てDBとみなして通す。明示的なフラグ（`-d`/`--dbname`/`-D`/`--database`/
  `-p`/`--port`/`-h`/`--host`）や接続 URI でデータベース接続情報を指定する際に、
  `spec-testing-` が含まれる接続を名乗ることで許可される。名乗らない localhost への
  書き込みは開発者の実データベースの可能性を排除できないので、常に止める

これは規約ではなく執行である。守らないコマンドはガードが実行前に止める。

### ホストポートを固定しない

`-p 5432:5432` のような固定割り当ては禁止。`-p 127.0.0.1::5432` か `-P` を使い、
割り当てられたポートを実行時に読む。開発者が使用中のポートと衝突しないため。

### 既定の隔離手段

ファイルの読み書きだけで完結するものは**一時ディレクトリ**。プロセスとして動く
ミドルウェア（データベース、キャッシュ、メッセージキュー）が必要なものは**使い捨て
コンテナ**。専用のボリュームを作り、終了時にボリュームごと破棄する。

コンテナを既定にしない。立ち上げのコストが高く、開発者のマシンのスペックを消費する。
一時ディレクトリで足りるものにコンテナを使わない。

### シードデータ

リポジトリにシード投入の手段があればそれを使う。無ければ、そのケースが必要とする
最小限のデータを `evidence/<case_id>/fixtures/` に置いて投入する。**開発用データベース
からデータを複製しない。**

### 立てた環境は納品する

Tier 2 で環境を立てたら、その作り方を**プロダクトコード側**に置く。
`compose.test.yml` のような形でリポジトリに残し、次回以降も再利用できるようにする。
テストアーティファクトのディレクトリには置かず、`report.md` からパスを参照する。

使い捨てではなく再現可能な環境定義なので、ワンショットスクリプトの混入禁止には
当たらない。

## Tier 3: 対象外

以下のいずれかに当たるものは `out_of_scope` に固定する。実行を試みない。

- **テスト環境の立ち上げ手順が判明していない。** リポジトリにも公式の標準手順にも
  根拠が無く、推測で組み立てるしかない
- 外部 SaaS への実アクセスが必要で、そのための認証情報を渡す必要がある
- ブラウザ操作で認証を突破する必要がある
- 開発者マシンのグローバルな状態を変える必要がある
- 開発用データベースへの書き込みが必要
- 実機や実環境が必須で用意できない
- 人間の目視確認が本質的に必要

### なぜ「手順が判明していない」を error ではなく out_of_scope にするか

原因が「試したが失敗した」ではなく「そもそも実行する手段が無い」だから。ここで
推測で環境を組み立てさせると、無人実行で最悪の事故が起きる。勝手に依存物を入れる、
勝手に設定を書き換える、間違った対象に接続する。

分類を誤ると、環境が用意されていないプロジェクトで `error` が量産され、本当の実行
失敗と区別できなくなる。**判定は生成時のレビュー合議が行う。実施時には行わない。**

### 外部サービスに依存する場合の抜け道

管理画面をブラウザ操作するのではなく、**開発環境に対して API トークンでアクセスする
経路が用意できるなら Tier 2 として扱える。** 読み取り専用トークンなら事故の幅も
限定される。この経路が無いなら Tier 3。

### 開発用データベース

読み取りは許可する。書き込みは禁止。緩めるなら「テスト用のデータベースを Tier 2 で
立てる」の一手だけにする。個別に緩められるようにすると、無人実行でその経路が必ず
使われる。

## 対象外に逃げるのを防ぐ

**Tier 2 の条件を満たすのに `out_of_scope` に落とすことを禁止する。**

放置すると、AI が楽をして対象外を量産する。「テスト可能」の判定が甘くなる方向に
壊れると、レポートは綺麗なのに何もテストしていない状態になり、かつそれに気づけない。

レビュー合議の判定軸に「対象外の判定が妥当か。Tier 2 でできることを対象外にして
いないか」を入れる。

## テストコードを書くときの規律

### 単体テストを第一選択にする

時間がかからず、外部依存を持たないものは単体テストとして書く。

### 実行できたものはコードとして残す

単体・結合・E2E のどれであっても、**テストコードとして実装できるなら実装し、
プロダクトコードとして納品する。** その場かぎりの手動確認で終わらせない。

E2E も例外ではない。ブラウザ操作の自動化で書けるなら書いて納品する。認証突破が
必要なものは Tier 3 なので実行しないが、ローカルで完結する E2E は Tier 2 として
実行でき、そのコードは残す価値がある。

### 落ちるテストを緑にする細工を禁止する

追加したテストが落ちた場合、**落ちたまま残す。**

以下をすべて禁止する。

- テストのスキップ指定や除外設定を付ける
- 期待値を実際の出力に合わせて書き換える
- アサーションを削る、または緩める
- テストを消す

落ちているテストを追加した PR はマージできない状態であるべきで、そこから直すのは
人間の仕事である。FAIL の修正はこのスキル群のスコープ外なので、緑にする権限も無い。

これはガードが機械的に執行する。

### 既存の単体テストスイートを汚さない

単体テスト以外を書く場合は以下を守る。

1. レベルごとに専用のディレクトリを掘り、その中に置く
2. 既存の単体テストの命名規則を使わない。既存が `*.test.ts` なら別の接尾辞にする
3. **既存の単体テスト実行コマンドがそれらを拾わないことを、実際にコマンドを走らせて
   確認する**

3 の手順は `collection-diff.mjs` を使う。追加前に単体テスト実行コマンドの一覧出力を
記録し、追加後にもう一度取得して突き合わせる。一覧が取れないランナーでは件数で
比べる。**この確認の実行コマンドと出力は証跡に残す。**

既存のテストランナーで動かすこと自体は構わない。分けるのは収集対象であって
ランナーではない。

### 環境の残留を確認する

Tier 2 で立てたコンテナ・ボリューム・ネットワークが片付いているかを、`env-snapshot.mjs`
の `collectEnv` / `verifyNoLeftovers` で確認する。立てる前に `collectEnv` で一覧を
取り、後片付けの後にもう一度 `collectEnv` を取って `verifyNoLeftovers` に突き合わせる。
差分（残留物）があれば片付けが不完全ということなので、そこで対処する。
**この確認の実行結果は証跡に残す。**

## ガードが止めるもの

テストスキルを起動したセッションでだけ効く。装填されていないセッションでは何も
止めない。

| ルール ID | 止めるもの |
|---|---|
| `force-push` | force push |
| `push-to-foreign-branch` | `spec-testing/` 以外のブランチへの push |
| `sudo` | sudo を伴う操作 |
| `global-install` | グローバルなパッケージ操作 |
| `prune-everything` | `docker system prune` などの一括削除 |
| `touch-foreign-resource` | `spec-testing-` で始まらないコンテナ・ボリュームの操作 |
| `compose-without-project` | プロジェクト名を分けない `docker compose` |
| `fixed-host-port` | ホストポートの固定割り当て |
| `remote-database` | localhost 以外のデータベースへの接続 |
| `remote-migration` | localhost 以外へのマイグレーション |
| `local-database-write` | 開発用データベースへの書き込み（Tier 2 の使い捨てDBを除く） |
| `destructive-migration` | データベースを落とす操作 |
| `authenticated-remote-request` | 認証情報つきの外部アクセス |
| `delete-test-file` | テストファイルの削除 |
| `write-ci-config` | CI 設定ファイルの変更 |
| `ci-config` | CI 設定ファイルへの Write / Edit |
| `add-skip` | スキップ指定・除外設定の追加 |
| `weaken-assertion` | アサーションを減らす、または期待値の書き換え・行の消失で緑にする編集 |
| `empty-test-file` | テストファイルを空にする書き込み |
| `guard-self-protect` | ガード自身の実装・設定ファイルへの Write / Edit |
| `self-disarm` | エージェント自身による `guard-hook.mjs disarm` の実行 |

止められたら、**迂回する形に書き換えて再実行しない。** 別の手段を選ぶか、手段が
無ければそのケースを対象外として理由とともに台帳に記録する。

対話中にガードを外したいときは、そのセッションの `session_id` を指定して外す。

```bash
node kiai-sp/lib/spec-testing/guard-hook.mjs disarm --session <session_id>
```

### 既知の穴として書き残す

`pip install` は単体では止めていない。プロジェクトの仮想環境への導入とシステムへの
導入を、フックから渡る情報だけでは区別できないため。`sudo` を一律で止めることで
`sudo pip install` は塞がるが、仮想環境が無いプロジェクトでの `pip install` 単体は
通る。

Bash からインタプリタ（`python3 -c`、`node -e` 等）を介してファイルを直接書き換えたり、
DB クライアントライブラリをスクリプト言語経由で呼び出したりする経路は、
`forbidden-bash.mjs` / `forbidden-file.mjs` のどちらの判定にも引っかからない。
コマンド文字列にはインタプリタの起動しか現れず、実際にファイルを書き換える処理や
DB への書き込みはインタプリタの内部で行われるため、静的な判定では捕まえられない。
レビュー合議でこの手口を警戒すること。
