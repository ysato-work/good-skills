# Phase 3 — 本文と行コメントの生成

## 入力を読む

書き始める前に、Phase 2 の結果を**ファイルから読み直す。記憶から再構成しない。**

1. `WORKDIR/thrust.json` を Read する。`thrusts` が展開部分に書く主眼、`fold_all` が `概要` に畳むかどうか
2. `WORKDIR/material.md` を Read する。任意枠の材料と読者が辿るリンクはここにある
3. `WORKDIR/pr-state.json` を Read する。番号コメントを作るかどうかがこれで決まる。判定は下記の節で行う
4. `WORKDIR/mode.txt` と `WORKDIR/body-state.json` を Read する。`mode.txt` が `create`、または `body-state.json` の `state` が `overwrite` なら、この Phase でタイトルも生成する。手順は下記の節にある

`thrusts` は配列の順序がそのまま展開部分の文の順序。並べ替えない。

ついで変更を表す `incidentals` は**展開部分に書かない。** 各要素の `where` の行に、番号なしの意図コメントとして落とす。`what` をそのまま書くのではなく、なぜそこを触ったかが分かる 1 文にする。読む順序には入れない。

## 通じる言葉で書く

読者は**このリポジトリに詳しくないエンジニア**。DB 用語・言語名・OSS 名のような一般的な技術語は通るが、このリポジトリの中でしか通じない語は通らない。水準の目安は「PM 向けの文書を書くくらい」。

**このリポジトリの中でしか通じない語を、説明なしで使わない。** 変数名・関数名・型名・内部 API 名がこれに当たる。

禁止しているのは語そのものではなく**説明なしの初出**。初出で説明してから使うのは通る。一度説明した語は以降そのまま使ってよい。

適用範囲は本文と行コメントの**全部**。本文には展開部分と `<details>` が含まれる。**行コメントを例外にしない。**

展開部分は上限 2 文で用語説明を置く余裕がないため、そこでは説明付きでも使えない。日常語に言い換える。

| 元 | 書き直し |
|---|---|
| `Vendor.enabled_features` を追加した | ベンダーごとに使う機能を選べる設定欄を足した |
| `applyFallback` を消していない | 今までの穴埋め処理を消していない |
| confidence 50 で埋める | 採点できなかった候補に仮の点をつける |

## 書くのは事実だけ

本文と行コメントに書いてよいのは、次の 2 つだけ。ここでいう本文は展開部分と `<details>` を指す。

- 差分から確かめられること
- この作業で実際にやったこと。走らせたコマンドとその結果、書いたテストがこれに当たる

次の 2 つは書かない。

- **これから誰かが何かをする話。** 予定、確認の段取り、引き継ぎ、別の作業に回す話。誰も決めていない段取りを書くと、読者はそれを決定事項として読む
- **書き手の評価・提案。** `〜すべき` `〜した方がよい` `〜が望ましい` のような文。事実ではなく意見で、レビュワーの判断を先取りする

どちらも Phase 4 の `禁止表現` が語で検出し、Phase 5 の問い 13 が見る。出たらその文を消す。事実を足して言い換えない。

| 書かない | 書き直し |
|---|---|
| 実機との突き合わせはリリース後の QA で確認する | 実機との突き合わせは行っていない |
| この処理は早めに直すべき | 消す。事実にする余地が無い |

## 読み手に届く日本語にする

本文と行コメントを書く直前に `references/ai-writing.md` を Read し、その規範に従って書く。**読まずに書き始めない。**

規範のうち「一文ごとに改行」を含む見た目の項目は、展開部分の型（21 バイト・最大 2 文）と衝突する。衝突したら展開部分の型を優先し、規範は `<details>` の中身と行コメントにだけ適用する。

## 丸括弧で補足しない

日本語の文の中に丸括弧 `()` と `（）` を書かない。例外は、物理名を出さないと相手の
作業や理解が進まないときの、論理名→物理名の短い言い換えだけである。物理名とは、
ファイル名・変数名・環境変数名・関数名など、コード上で使われている識別子を指す。
基本は物理名を書かない方が短くて読みやすい。書かなくて済むなら書かない。

鉤括弧 `「」` `『』` は対象外である。

この例外の判定はブレていい。判定に迷ったら、丸括弧を消して文を分ける。

このルールの適用範囲は本文と行コメントの全部であり、PR タイトルは対象外とする。

補足を丸括弧に押し込む代わりに、独立した文にするか、消す。展開部分に出た丸括弧は
Phase 4 の `展開部分に丸括弧を禁止` が違反として拾う。`<details>` の中身と行コメントに
出た丸括弧は一覧に載り、Phase 5 の問い 14 が例外に当たるかを見る。

「鉤括弧は対象外」とあるのは、鉤括弧という記号そのものを禁止しないという意味である。
鉤括弧の中にある丸括弧は対象である。読者が読む文に出るなら拾う。

ルール文をこのスキル向けに書き換えていないのは、`wakaranai` と `kimoi` に同じ文言を
保つためである。

失敗例:

元の言いたいこと「テストが通ったことを確認しました」

ダメ、丸括弧に補足を押し込んでいます:
「テストが通ったことを確認しました（単体テスト 42 件と統合テスト 8 件がすべて成功）」

良い、文を分けています:
「テストが通ったことを確認しました。内訳は単体テスト 42 件と統合テスト 8 件で、
すべて成功しました。」

元の言いたいこと「セッションID を環境変数から取ります」

ダメ、物理名を出す必要が無いのに丸括弧に入れています:
「セッションID（環境変数から引き継がれる ID）を環境変数から取ります」

良い、論理名から物理名への短い言い換えです。実装者は環境変数名を知らないと作業が
進まないので、物理名を出す必然性があります:
「セッションID `CLAUDE_CODE_SESSION_ID` を環境変数から取ります」

## 置き場所

| 場所 | 中身 |
|---|---|
| PR タイトル | 主眼の文に、過去 PR の型を被せた 1 行。**新規作成時と `--overwrite` 指定時のみ。それ以外で既存 PR のタイトルは触らない** |
| 本文・展開部分 | 主眼の文だけ |
| 本文・`<details>` | `変更のサマリー` は必須。`ドキュメント` と `テスト` は条件付き。任意枠は 0〜2 |
| 行コメント。番号あり | 読む順序と、そのコードが何をやっているか。1 行 |
| 行コメント。番号なし | 普通ならこう書くところを敢えて外している箇所の意図。ついで変更もここ |
| レビュー本体 | 「1 から N の番号順に読んでください」 |

**読む順序を本文に置かない。** コードの場所に付ける方が読みながら辿れて、「1 で用意した X を使う」のような前段参照も書ける。

## PR タイトルの生成

`WORKDIR/mode.txt` が `create` のとき、または `WORKDIR/body-state.json` の `state` が `overwrite` のときにだけ実行する。それ以外の `edit` モードではタイトルを生成しない。既存 PR のタイトルは触らない。過去タイトルも取らない。

タイトルを書く直前に、今のリポジトリの自分の過去タイトルを取る。タイトルを書いたあとで取ってはいけない。

```bash
gh pr list --state all --author @me --limit 20 --json title > <WORKDIR>/past-titles.json
```

1 発で足りる。番号を取ってから 1 件ずつ view しない。他リポジトリ・他 org は見ない。`--repo` を付けない。

保存先: `WORKDIR/past-titles.json`。`gh` の JSON をそのまま入れる。中身の例:

```json
[{"title":"feat: add slop check"},{"title":"PR 説明文スキル"}]
```

取得コマンドが失敗したら、`WORKDIR/past-titles.json` を残さない。途中まで書けていたら消す。主眼の文をそのままタイトルにする。型合わせをしない。

取得結果が 0 件でも型合わせをしない。ファイルの中身が `[]` のときも同じである。主眼の文をそのままタイトルにする。ファイルは `gh` の JSON のまま残す。

取れたら `WORKDIR/past-titles.json` を Read する。過去タイトルを見て、「こういうときにこういう形式にするんだな」を雑に類推する。その形式を主眼の文に被せる。

- **型** — 接頭辞の有無、日英、体言止め、Conventional Commits など、タイトルの形。中身ではない
- **被せる** — 主眼の文の意味は変えず、類推した型に合わせて 1 行にする。主眼を別の文に書き直さない
- 最頻・過半数などの数え上げルールは置かない
- 型がバラバラでも、参考にして類推する。やめない
- 中身は主眼の文。型だけ借りる

被せる元:

- ソース: `WORKDIR/thrust.json` の `thrusts` 配列
- 主眼が 1 つ → その文を被せる元にする
- 主眼が複数 → 配列の先頭要素を被せる元にする。並び順は Phase 2 で確定済み

例。型だけ借りる。中身は主眼のまま。

- 過去が `feat: add slop check` で、主眼が `採点失敗時の 50 埋めをやめた` → `feat: 採点失敗時の 50 埋めをやめた`
- 過去が `PR 説明文スキル` で、主眼が `採点失敗時の 50 埋めをやめた` → `採点失敗時の 50 埋めをやめた`。体言止めに寄せるために「50 埋めの廃止」へ書き直すのは禁止

保存先: `WORKDIR/title.txt`。末尾改行を含めず 1 行にする。

タイトルは Phase 4 の表層検出を通す。検出するのは禁止語、絵文字禁止、50 文字上限の 3 つである。違反があれば Phase 6 のループで直す。直しのときに過去タイトルを取り直さない。型を数え直さない。

## 展開部分

**箇条書きという形式を使わない。** 箇条書きを作ると、埋めるものが無くても埋めてしまい、関数名の羅列になる。形式を作らないことで防ぐ。

## `<details>`

出す枠と順番は次。出さない枠は飛ばす。任意枠は AI がこの列のどこに挟むかを考える。

1. 概要。主眼が 3 つ以上で畳むときだけ出す。畳まないときは展開部分がこれになる
2. 変更のサマリーは必須である
3. テスト。文書だけではないときに、書くと判断したら出す
4. ドキュメント。辿るリンクがあるときだけ

summary の固定文字列は予約タイトルだけ。`なぜこうしたか` のような例タイトルで枠を起こさない。

### 変更のサマリー

必須の枠。何を変えたかの事実。概要の言い直しにしない。なぜ・経緯は書かない。構造化箇条書き。

- 1 段階目は見出しだけ。`- ` を除き UTF-8 21 バイト以内
- 2 段階目に具体
- 3 段階目は 2 段階目の補強が必要なときだけ。4 段階目は置かない
- 1 段階目だけで終わらせない
- 中身は 750 バイト以内

### ドキュメント

読者が辿る関連リンク全部。無ければ枠ごと作らない。「ない」と書かない。リンクは 1 段なのでタイトルではなく、21 バイト制限の対象外。ネストしたら掛かる。750 バイト上限は掛けない。

### テスト

文書だけの変更では枠ごと作らない。「テストなし」と書かない。文書だけでないときの要否は AI。

構造化箇条書き。1 段階目は次。1 段階目に 21 バイト制限は掛けない。

- テストしたこと
- テストしてないこと

**`テストしてないこと` には、やっていない事実だけを書く。** その後に誰が・いつ・どこで確認するかは書かない。「書くのは事実だけ」を参照。

### 任意枠

0〜2 個。出す条件は「これは書いた方がよい」と判断したこと。0 個でよい。枠を埋めるために書かない。予約タイトルは使わない。文章でも箇条書きでもよい。各 750 バイト以内。

**タイトルはフリーハンド。分類のメニューから枠を起こさない。**

**`影響範囲`・`破壊的変更`・`バグがあった場合の最大被害` を任意枠にしない。** いずれも差分から確かめられない推測にしかならないので枠ごと廃止した。`<summary>` に `影響範囲`・`今後の対応`・`今後の予定`・`残課題`・`フォローアップ` のいずれかを含めると Phase 4 が違反にする。いずれも差分から確かめられない推測か、これから誰かが何かをする話にしかならない。

1. 先に中身を決める。書いた方がよいと判断したことだけ
2. 中身が決まってからタイトルを付ける。その中身を指す語にする。リストから選ばない
3. `なぜ` `経緯` `捨てた選択肢` `知らない概念の説明` は安易に使わない。選んでもよいが、中身に即したより具体的なタイトルがあることが多い

出力サンプルに任意枠のタイトルは置かない。

## 知らない概念の説明

**読者がその語を知っているかは判定できない。** リポジトリに既出であることは、読者が知っている証拠にならない。人間はリポジトリの中身を全部知らない。

判定できるのは語の側の事実だけ。

> **その語はこのリポジトリの外でも通じるか。** 通じるなら説明しない。通じないなら、日常語に言い換えるか、初出で説明してから使う。

説明は 1 行に収める。展開部分には説明を置けないので言い換える。details に載せるなら任意枠。タイトルは「知らない概念の説明」にしない。

## 行コメント

**番号コメントと意図コメントは別コメントにする。** 同じ行に両方付く場合も、1 つのコメントにまとめない。

番号コメントは 1 行。読む順序と、そのコードが何をやっているかを書く。前段を参照してよい。たとえば「1 で用意した X を検証する」のように書く。

意図コメントは番号なし。普通ならこう書くところを敢えて外している理由を書く。ついで変更もここに置き、読む順序には入れない。

## 番号コメントの投稿条件

`WORKDIR/pr-state.json` の `has_review` を読んで決める。**目視や記憶で判断しない。**

| `has_review` | 番号コメント |
|---|---|
| `true` | **作らない。** 意図コメントだけを作る |
| `false` | 作る。前回の自分の番号コメントがあれば Phase 7 で削除してから貼り直す |

`--force-comments` が指定されているときは `has_review` の値に関わらず番号コメントを作る。`true` の PR で番号コメントを二重にすることになるが、これはユーザーが明示的に選んだ挙動として扱う。

レビューが 1 件でも付いている PR で番号コメントを作らないのは、一度レビューされた後は指摘を直している段階で読む順序の価値が下がるため。GitHub のレビューコメントはコミットが積まれても outdated 表示で残るため、投稿を続けると新旧の番号が混在して「番号順に読んでください」がどのセットを指すか分からなくなる。

レビューが付く前の再実行で貼り直してよいのは、まだ誰の目にも触れていないため。削除の手順は Phase 7 にある。

**意図コメントはレビュー後も作る。** 新しい差分についても価値があるため。

## 出力

- `WORKDIR/body.md` — 本文。マーカー行はまだ付けない。Phase 7 で付ける
- `WORKDIR/line-comments.json` — 行コメントの配列
- `WORKDIR/title.txt` — PR タイトル。`create` モード、または `--overwrite` 指定時だけ
- `WORKDIR/past-titles.json` — 過去タイトル。`create` モード、または `--overwrite` 指定時だけ。取得成功時のみ作る。失敗時は無い

```json
[
  {"path": "lib/score.mjs", "line": 42, "numbered": true, "text": "1: 採点できなかった候補に仮の点をつける経路"},
  {"path": "lib/score.mjs", "line": 42, "numbered": false, "text": "今までの穴埋め処理を消していないのは、他の 3 スキルがそこを通っているため。"}
]
```

## 出力サンプル

主眼が 1 つの場合のサンプル。

本文:

~~~markdown
採点できなかった候補に仮の点をつけて先に進むのをやめ、3 回やり直して駄目なら止めるようにした。

<details>
<summary>変更のサマリー</summary>

- 採点変更
  - 失敗した候補を 50 点で埋めなくした
  - 3 回やり直して駄目なら止める

</details>
~~~

レビュー本体:

~~~
1 から 4 の番号順に読んでください。
~~~

番号コメント:

~~~
lib/score.mjs L42          1: 採点できなかった候補に仮の点をつける経路
lib/score.mjs L61          2: 1 を通らないとき、3 回まで再試行して超えたら止める
lib/validate.mjs L18       3: 2 の前提が崩れないよう閾値 51〜99 を強制する
references/phase-4.md L30  4: 1〜3 の挙動を手順書に反映
~~~

意図コメント。番号なしの別コメント:

~~~
lib/score.mjs L42
今までの穴埋め処理を消していないのは、他の 3 スキルがそこを通っているため。
消すと PR レビュー用の別スキルが落ちる。
~~~
