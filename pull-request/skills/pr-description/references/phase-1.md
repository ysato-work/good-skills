# Phase 1 — 素材集め

**価値は差分の外にしかない。** なぜ変えたのか、何が壊れていたのか、検討して捨てた選択肢、読者が辿るリンク。どれも差分に写っていない。差分だけ見て書くと、差分の言い換えしか出てこない。

## 集める先

- リンクされたイシューの本文とコメント
- この PR のコミットメッセージ全部
- 同じファイルを触っている直近の過去 PR
- PR にリンクされた議論
- リンクされたイシューを閉じてよいかの判定。詳しくは下記「issue を閉じてよいかの判定」にある
- 読者が辿るべき関連リンク。設計書、Issue、関連 PR、README の該当、Notion、チケットがある

## 手順

1. 上記を読み、`WORKDIR/material.md` に書き出す
2. 書き出す内容は「なぜ変えたか」「何が壊れていたか」「検討して捨てた選択肢」「読者が辿るリンク」に絞る。差分から読めることは書かない
3. 何も集まらなかった場合も `material.md` を空で作る。**空であることが次の Phase の入力になる**

## 素材が集まらなかったとき

イシューが無く、コミットメッセージが `fix` だけ、という状態はある。その場合は差分から起こすしかない。

**素材が無いことを隠さない。** 任意枠は、書かないとレビュワーが判断を誤るほど重要なことがあるときだけ作る。無いのに枠を埋めてはいけない。リンクが 1 本も無ければドキュメント枠は作らない。

## issue を閉じてよいかの判定

`fix:` を書くと、この PR をマージしたときに GitHub が issue を閉じる。閉じてよいかを差分で確かめてから書く。

1. issue の手がかりを探す。コミットメッセージ・ブランチ名・差分に出てくる `#<数字>` を見る。`edit` モードでは既存 PR の本文も見る。`create` モードでは PR がまだ無いので見ない。見つからなければ、そこで終わって空の記録を書く。**推測で issue を探し回らない**
2. issue の本文とコメントから「完了と言える条件」を 1 行ずつ書き出す
3. 条件ごとに、差分のどの行がそれを満たすかを対応付ける
4. 全部に対応が付いたときだけ `closure` を `fix` にする。1 つでも付かないとき、条件が読み取れないときは `ref` にする。**PR の向き先がリポジトリの既定ブランチでないときも `ref` にする。** GitHub は既定ブランチ以外が向き先の PR ではキーワードを解釈しない。issue もリンクされない。向き先は `create` モードなら `WORKDIR/base.txt`、`edit` モードなら対象 PR の base ブランチである
5. 条件と対応を `WORKDIR/issue-verdict.json` に書き出す

```json
{
  "issues": [
    {
      "ref": "#123",
      "closure": "fix",
      "conditions": [
        {"text": "採点に失敗した候補を 50 で埋めない", "evidence": "lib/score.mjs の 42 行目"}
      ]
    }
  ]
}
```

issue が 1 つも見つからなくても、このファイルを必ず書く。そのときは `{"issues": []}` である。`body-state.json` と同じ扱いで、判定をスキップした場合でも書く。
