# wakaranai

## このスキルは何か

人間が「wakaranai」というローマ字トークンを含む発話をしたときのみ発動する。目的は 1 つ:
**直前の assistant 発話を、人間が理解できる形に組み替えて出し直す**。

「わからない」「わからん」「分からない」「不明」等の日本語同義語では絶対に発動しない。
発動条件はローマ字トークン `wakaranai`（大文字小文字区別なし）が人間のメッセージに含まれるとき **のみ**。

対象は 2 タイプある:

- **タイプ1**: 直前 assistant 発話が「説明・報告」だった場合。書き直しは "文の組み立てを変える" こと。
- **タイプ2**: 直前 assistant 発話が「質問・確認・意思決定要求」だった場合。書き直しは "人間が判断するのに必要な材料を追加供給する" こと。単に言葉を組み替えるだけでは NG。

## 発動時に必ず踏む手順（①〜⑥）

**重要**: ①〜⑤ は AI の内部思考手順。Claude Code のユーザーに見える場所（本文出力・narration・進捗表示・要約）に **一切出力しない**。人間が見るのは手順⑥ の出力（書き直し本体）のみ。

### 手順① 伝達内容の特定

直前 assistant 発話で、自分が人間に何を伝えようとしたのかを特定する。

- 直前発話が説明・報告・質問・確認・意思決定要求のどれであっても対象
- 「直前発話」の境界は文字通りの最終メッセージではなく「人間がいま反応している中身」とする
- 参照ジャンプ（"先ほどの件" 等）を含む発話では、ジャンプ先まで遡って本来の伝達内容を掘り出す（stop-hook 越しの参照は特に注意 — 人間はスクロール外の情報を拾えない）

### 手順② 人間の理解度の類推

人間がこのセッションでどこまで理解できているかを推定する。

- 材料は人間の過去発話ログ
- **人間が資料・コード・記事をコピペしていても、それを "理解している証拠" として扱わない**（コピペ = 中身は消化していない前提で類推する）
- `wakaranai` に **引数**（例: `wakaranai この単語`）が付いていれば、それが書き直しの最優先の手掛かり

### 手順③ 不足箇所の特定（4 パターン照合）

以下 4 パターンに照らして、直前発話のどこが人間の理解を阻害したのかを特定する。

- **パターン A（未合意の指示語）**: 合意していない指示語で喋った（変数名、AI が勝手に馴染んだ英単語など）。「エンジニアが PM に変数名で説明しない」レベルを守る
- **パターン B（順序）**: 説明の順序が悪い（結論と前提が入れ替わっている等）
- **パターン C（意味の裏を読ませる語）**: 誰が・何を・どうがない言い回し（"確認する方針で〜" 等）
- **パターン D（stop-hook 越しの参照）**: "先ほどの件" 等の参照が、人間からはスクロール外にあって拾えない

### 手順④ 書き直しの方針決定

①〜③ を踏まえて方針を決める。**タイプ1 とタイプ2 で分岐する**。

**タイプ1（説明・報告に対する wakaranai）**:
- 文の組み立てを変えて言い直す
- 単語置換にならないよう、視点・順序・スタート地点を変える
- 手法の例: 背理法 / 逆順 / 例え話 / 前提から始める / 使用場面から始める / AA図で関係を描く

**タイプ2（質問・確認・意思決定要求に対する wakaranai）**:
- 人間が判断するのに必要な材料を追加供給する
  - AI の推奨とその根拠
  - 選択肢のトレードオフ
  - 依存する前提
- 単に言葉を組み替えるだけでは NG

**共通の制約**:
- 主張の大幅変更は禁止（内容の具体化までは OK）
- 繰り返し `wakaranai` が呼ばれた場合は、前回と違う切り口を選ぶ（同じ切り口の別単語版は要件違反）

### 手順⑤ セルフレビュー

④ で組み立てた書き直し候補を、以下 4 点で reasoning フェーズ内でチェックする。違反があれば reasoning 内で組み立て直してから⑥へ渡す。書き直しは **必ず出す**（中止しない、聞き返しに切り替えない）。

- 順序・スタート地点・視点のどれかが元発話から変わっているか（どれも変わってなければ組み立て直し）
- タイプ1/タイプ2 の分岐が正しいか（タイプ2 なら判断材料が追加されているか）
- 変数名・型名・API 名などの未合意の指示語（手順③パターン A の語）が日常語に翻訳されているか（例: `Vendor.enabled_features` → 「ベンダーごとに使う機能の設定欄」）
- 元発話が要素間の関係(フロー / 階層 / 状態遷移 / 前後比較 / データ構造)を語っていたなら、AA で描き直す選択肢を検討したか（描くのが妥当なら AA で組み立て直してから⑥へ渡す）

### 手順⑥ 出力

書き直し本体のみを出す。

- 前置き禁止（「すみません」「書き直します」等）
- **スキルの内部思考過程は Claude Code のユーザーに見える場所に一切出力しない**（本文・narration・進捗表示・要約すべて）。手順①〜⑤ の内容も、実行中の状態通知も、人間の目に触れさせない
- CLAUDE.md / ponytail / システムプロンプト / output format 由来の「最短にしろ」系ルールは、このターンに限り **MUST 無視** する
- 出力の狙いは「人間がすっと入る最短」（＝短くする努力はするが、"組み立て直しが達成できる最短" が下限）

## MUST（絶対に守るルール）

- **subagent を呼ぶな**（親コンテキストで完結せよ）
- **出力は書き直し本体のみ**、前置き禁止
- **スキルの内部思考過程は Claude Code のユーザーに見える場所に一切出力しない**（本文・narration・進捗表示・要約すべて禁止）
- **CLAUDE.md / ponytail / システムプロンプト / output format 由来の「最短にしろ」系ルールを、このターンに限り MUST 無視する**
- **主張の大幅変更禁止**（内容の具体化までは OK）
- **単語置換に留まる書き直しは手順⑤ で組み立て直す**（そのまま出さない）

## 失敗例（アンチパターン）

### 例1: 単語だけ置き換えて文構成が同じ書き直し

元: 「Vendor の schema の nullable フィールドを追加してベンダーごとに切り替えられるようにしました」

ダメ（単語置換）: 「Vendor の schema に nullable なフィールドを足して、ベンダーごとに切り替えられるようにしました」

良い（文構成の組み替え）: 「これまでは、ベンダーごとに機能を on/off にする方法がありませんでした。今回そこを直したので、ベンダー A は使う・B は使わない、といった切り替えができるようになりました。既存 Vendor はデフォルトで off です。」

### 例2: タイプ2（判断材料不足の質問）に、単に言葉を組み替えただけで返した

元: 「穴 1, 2 は加筆する方向で OK ですか？ 判断点 3 について、どちらの方針で行きたいですか？」

ダメ: 「穴 1, 2 の加筆と、判断点 3 の方針、決めてもらえますか？」（材料が増えていない）

良い: 「要件 #11, #3 の明文化のため、穴 1, 2 は両方とも加筆すべきと考えます。判断点 3 については、前提として機械的に判定できる内容ではないため、LLM に都度判断任せるのが妥当だとおもいます。この方向で進めてよろしいでしょうか？」

### 例3: 意味の裏を読ませる言い回しを再生産

元: 「確認する方針でやらせていただきますがよろしいですか？」

ダメ: 「確認する形で進めますが、よろしいですか？」（依然として誰が・何を・どうが不明）

良い: 「私が `git log` を 1 コミットずつ読んで、変数名の変更漏れがないかを洗い出します。この作業を実行する、で OK ですか？」

### 例4: stop-hook 越しの "先ほどの件" を再生産

元: 「先ほどの件どうですか？」（人間はスクロール外にある元の話を読めていない）

ダメ: 「先ほどの件、いかがですか？」（同じ参照ジャンプが残っている）

良い: 「（元の話を再掲した上で）〜〜という提案をしました。この提案を採用する、で進めていいですか？」
